# Project Z 项目宪法（Flutter 重写版）

> 本文件是「点点」重写工程的最高工程约定。所有 spec、plan、tasks、代码与评审都必须遵守；
> 与旧版 `AGENTS.md`（uni-app）冲突时，以本文件和后续 Flutter 版 `AGENTS.md` 为准。

## 第一条：本地优先，数据属于用户

1. 业务数据默认只存本机 SQLite，不上传云端；AI 请求只发送完成当前任务所需的最小上下文。
2. 任何联网能力都必须可关闭、可解释，并在 UI 上明确标识「将发送什么给哪个模型」。
3. 备份/导出是本地文件，格式公开、可读、可恢复；删除数据必须真正删除关联数据。
4. API Key 存平台安全存储（Keychain / Keystore / Windows Credential Manager），
   不写入数据库、日志、崩溃报告或仓库。

## 第二条：AI-native 是一等设计原则

1. **AI 不是附加页，而是默认协作方式**：目标设定、执行记录、复盘分析、知识沉淀四个环节，
   都必须有「一句话交给 AI」的入口，同时保留完整的手动路径。
2. **自然语言进，结构化数据出**：AI 输出必须经过 schema 校验，落库前可预览、可修改、可撤销；
   禁止把自由文本直接当作业务事实写入。
3. **上下文由系统编排**：统一的 Context Builder 负责收集项目、里程碑、日志、知识、历史对话，
   做预算裁剪与脱敏；禁止各页面自行拼接 prompt。
4. **工具调用可审计**：AI 只能通过白名单工具读写本地数据；写操作必须用户确认，
   每次调用记录工具名、参数摘要、结果与耗时。
5. **失败可降级**：无网络、无 Key、模型报错时必须退回手动流程与本地模板，
   不允许出现「没有 AI 就不能用」的核心路径。
6. **可评估**：Prompt、模型、工具 schema 版本化；关键 AI 流程用固定样例做回归测试，
   不靠「感觉变好了」验收。
7. **人保持最终决定权**：AI 给出建议、草稿、候选，不自动改目标、不自动删数据、不自动发布。

## 第三条：SDD —— 先规格，后代码

1. 每个可交付能力先有 `spec.md`：用户故事、验收场景、边界与非目标；再写 `plan.md` 与 `tasks.md`。
2. 代码实现必须能追溯到 spec 中的用户故事或验收项；无法追溯的改动先补规格。
3. 规格变更与代码变更同一次提交，禁止「代码先行、文档后补」。
4. 技术决策写入 `plan.md` / `research.md`，包含取舍理由与被否方案，避免重复踩坑。

## 第四条：TDD —— 测试先行

1. 领域逻辑、数据访问、AI 解析、同步/导入导出：先写失败测试，再实现，再重构。
2. Repository 测试使用内存 SQLite 与真实迁移；网络层使用 mock/fixture，不在单测里打真实 API。
3. Widget 测试覆盖关键交互与空/错/加载三态；关键页面加黄金图测试（至少浅色 + 深色）。
4. 合并门槛：`dart format` 无差异、`flutter analyze` 零 issue、`flutter test` 全绿；
   涉及平台能力时至少通过对应平台编译。
5. 不为覆盖率写无意义断言；以「验收场景是否被测试表达」为判断标准。

## 第五条：能复用就不手搓

1. 优先选择维护活跃、star/likes 高、许可证宽松的包；引入前记录理由与替代方案。
2. 基础组件（导航、表单、图表、Markdown、文件选择、安全存储、窗口管理）不自研。
3. 只有满足以下之一才自研：包不满足三端、包已停维护、需求是产品核心差异化、
   引入成本高于实现成本。自研必须在 `plan.md` 说明。

## 第六条：一套代码，三端自适应

1. Windows / Android / iOS 共享业务与数据层；平台差异收敛在 `platform/` 适配层。
2. UI 采用响应式布局：手机底部导航，桌面 `NavigationRail` + 多栏；禁止两套页面树。
3. 所有平台相关插件必须有抽象接口与假实现，保证其余两端可编译、可测试。
4. iOS 代码在 Windows 上不能编译，必须由 CI 的 macOS job 守护；不得以「本机通过」代替三端验证。

## 第七条：可观测与可维护

1. 统一日志分级与脱敏；错误上报默认关闭，开启时不含正文与密钥。
2. 数据库迁移只增不改：每个 schema 版本一个 migration，附迁移测试。
3. 公共能力单一入口：数据库走 Repository、AI 走 AiGateway、设置在 SettingsRepository。
4. 小步提交：一个可验证单元一个 commit；提交信息说明「为什么 + 如何验证」。

## 第八条：设计为用户服务，不照搬旧债

1. 旧版工作流是要迁移的资产，旧版页面结构、交互细节、遗留 bug 不是。
2. 每个旧功能迁移前先回答：用户真正要完成什么？能否用更少步骤完成？AI 能否代劳？
3. 视觉遵循 Material 3 与统一设计令牌；先保证信息层级、可达性与深浅色，再谈装饰。
4. 文案中文优先，术语一致；空状态必须告诉用户「下一步做什么」。
